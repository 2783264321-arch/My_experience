## 当前路线

**以首场 baseline 为对照，先查清宽带目标的错类和排序问题，再选择改动。**

- **已确定的输入规格。**原生 STFT 为 `F×512`，其中频率格数 F 随观测带宽变化。当前 baseline 用 0.7 ms 单窗、2048×512 单通道粗细视图和 YOLO11s-C1-DirectReg。新的表示或模型可以作为另一个实验，与该基线比较。
- **当前参考结果。**`best_corrected.pt` 在固定的 1,543 个验证样本上报告 mAP@0.5 为 0.6427、AP75 为 0.5945，忽略类别的 AP@0.5 为 0.9046。旧训练曲线使用裁框修正前的评测口径。完整权重与预测在服务器运行目录，公开仓库以代码和报告为主。 [执行状态](../status.md) · [修正后验证](../../reports/stage5_results.md)
- **下一项实验。**冻结 `best_corrected.pt`，在完整验证集上做粗图、细片与联合预测的归因。依据结果决定优先改视图合并、分类复核还是置信度排序。 [OpenCode 独立审查](opencode-review.md)

## Codex 的两项审查发现

1. 完整验证的每视图保留上限是 300，单样本入口写的是 1,000。比较新方案时以产生 0.6427 的完整验证实际配置为参照，先核对两入口的一致性。 [验证入口](../../scripts/validate_run.py) · [单样本入口](../../src/signals/infer.py)
2. 分类加权微调将同一项权重乘了两次。项目包装了 BCE，而 Ultralytics 8.4.155 也读取 `model.class_weights`，所以该分支的实际权重是平方。首场 baseline 的加权参数为零。若重新研究加权，先验证只乘一次，再从相同权重出发做单变量对照。 [项目实现](../../src/signals/train.py) · [上游损失实现](https://github.com/ultralytics/ultralytics/blob/v8.4.155/ultralytics/utils/loss.py#L395-L400)

## 首个实验的执行口径

OpenCode 在完整 1,543 个验证源上复核了每视图上限 300 与 1,000，两次报告的 mAP50、预测数量及边界扣留数量一致。入口参数可随本轮顺手对齐，验证参照采用 300。分类权重平方偏差也已核实，保留该次微调记录供解释，单次加权的效果仍待对照。 [复核结果](opencode-review.md)

1. 维持同一权重和完整验证集，跑一次所有视图，记录来源。在全局合并前分出粗图、细片、联合三组，再各自执行相同的全局 NMS 与每样本 100 框上限。联合组先复现 baseline mAP50 0.642701，并核对预测总数 65,025。
2. 按 `0/1/2`、`3/4/5` 和 `10/11` 汇报类别 AP、忽略类别的召回、TP/FP/FN，配少量代表性错例。将错类、重复和背景误检分开，记录边界扣留和近重复真值的影响。重叠框先按原有一对一规则匹配，保留真实近同框实例。
3. 按结果给出一个首选改动。正确框常被打错类，先试候选框分类复核。高分错误主要由某个视图引入，先试按来源重评分或合并。若有更直接的解释，在结果里写明依据。交付三组指标、关键错例和下一项建议，结果写回本共享目录。实验使用现有权重与验证集。

## 协作方式

- 开工前先拉取最新提交，读此页与相关报告。完成后提交简短更新，写清依据的提交或运行、结果及建议的下一步。
- 双方可以审查并修订路线。遇到结论冲突，写清各自掌握的证据与适用条件，优先做小规模对照。用户已确认的规格单独列出，探索参数由执行方结合证据调整并记录。
- 给项目负责人先说进展、判断、下一步。复核所需的配置和数据口径放在链接里。
