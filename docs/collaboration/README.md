## 复数 STFT 粗图前端验证

### 研究动机与取舍

项目要研究的是**信号表示怎样影响端到端时频检测**。原生功率 STFT 让模型看到能量在时频上的分布。我们希望让整条检测流程看到复数系数，实测这是否能改善定位和识别，尤其是靠全频粗图获得完整框的 20/40 MHz Wi-Fi 调制类别。此前的 `128×256` 候选裁块试验提供了单独的分类诊断。

细片能够直接沿频率截取原生复数系数，粗图要把整个观测带宽放到 2048 行，取舍主要发生在这里。粗细视图应有相同的通道定义，当前优先实部和虚部。全频图的每行应对应明确的物理分析频率或子带。数据集采用 `Fs=B`。整段 IQ 降采样会缩小可观测频带，选定窄子带以后可以再探索抽取。希望用可说明的信号分析算子来构造粗图，并明确它为了固定尺寸舍弃了哪些信息。

两种复数粗图都以 `2×2048×512` 为目标。细片沿用 0.7 ms 复数 STFT、原生 `F×512` 和 Baseline-1 的频率切片位置。粗细共享现有 512 个帧中心与以 MHz 表示的全局频率坐标。两路频率格距可以不同，标签和输出回映各用自己的格距和偏移。 [当前 STFT](../../src/signals/stft_fast.py) · [视图和标签](../../src/signals/data.py) · [坐标回映](../../src/signals/infer.py)

### 第一轮观察与复核

- OpenCode 在 14 个 fit 样本、76 个真值实例上验证了相同帧中心和全频坐标映射，并用合成单音验证帧中心相位校正。幅度标定需要明确目标。PSD 归一化用于谱密度，相干增益归一化用于比较单音幅度，偏格单音仍受窗响应影响。 [OpenCode 前端核查](opencode-complex-coarse-frontend.md) · [详细报告](../../reports/complex_coarse_frontend_validation.md)
- 原始 train 的 34,755 个标注时间段都与至少一个 2048 点短窗相交。80 MHz、150 ms 的窗口覆盖约 8.7%，连续信号仍可能在相邻列都有有效测量，列内短突发的风险需要单独检查。报告中的 157 个弱列来自真值内 17,619 列，复算为 0.89%。150 ms 组的共同约 2.94 ms 边界 p90 碰到了向外搜索 10 列的限制，应报告触边数，靠已知边界的合成突发补测。原始 train 最短标注为 1 ms，发布的 76 个实例里也有 3 ms。 [测量实现](../../scripts/validate_complex_coarse_frontend.py) · [汇总 JSON](../../reports/complex_coarse_frontend_summary.json)
- 已测的复数频率池化是矩形和单带 Hann。50% 重叠滤波器组仍是候选，已有约 0.1 秒计时来自当前池化。重叠有机会改善频带交界的响应，带内不同相位合成时仍可能相消。它沿用长窗的帧位置，有效时间响应需要用短突发检查。 [当前池化代码](../../scripts/validate_complex_coarse_frontend.py#L112-L153)

### 下一轮共同决定粗图前端

| 候选 | 为什么保留 | 主要代价 |
| --- | --- | --- |
| 直接 2048 点复数 STFT | 原采样率、全频 2048 点 FFT、与细片同一帧中心。输出是定义清楚的复数短窗测量，额外开销低。 | 长观测的帧之间有空档。整框常能命中窗口，其内部短突发或连续调制线索可能保留不足。 |
| 0.7 ms STFT 到 2048 个重叠复数频带 | 可复用已有长窗系数。频带重叠可能补足单带 Hann 的带边低谷。 | 一带输出一个复数值会丢掉带内自由度，仍可能相消。频带中心、带宽、权重、相位和幅度参考，以及实际开销都要明确。 |

以原 Baseline-1 0.7 ms 功率粗图作为能量与时间轮廓的参照。建议复用上一轮 IQ 样本，补一组有明确真值的合成信号。扫过带中心、两带交界和观测带边缘的单音，观察相邻输出与频率偏移。在同带双音中改变相对相位，检验复数相消。把短突发移到窗中心和窗间，量化时间响应与边界偏差。真实混合 IQ 重点检查长观测的宽带完整性和短突发的能量可见性。

若实现重叠频带，请先按原生频率格校正到帧中心，再做复数合成。记录频带中心、覆盖范围、权重归一化、峰值/邻带响应和前端耗时。若报告聚合相干度，复数分子与功率分母采用相同的一组权重，记录幅度标定方式。稠密短窗的功率曲线可用于识别空档影响，时间覆盖依赖实际的 hop 上限。

**希望 OpenCode 给出自己的判断。** 稀疏 STFT 如果足以为宽带目标提供可用的时频证据，简单和低开销本身是收益。若重叠方案在带边或短突发上有实质改善，结合耗时和相消情况考虑采用。若两条路的实测取舍都不理想，可以提出另一种信号域构造，说明它牺牲什么、能用哪组小实验验证。交付两种前端的证据、推荐选择和仍有疑问的情况。本轮范围是前端对照。

### 这轮结果怎样决定后续检测实验

选定一种候选以后，才值得投入训练预算。由**同一份新粗细复数系数**分别导出单通道功率和双通道实虚部，在同一批划分、切片、标签、合并、模型主体和训练预算下做小规模端到端对照，分开看宽带错类、定位召回、窄带表现和计算开销。既有 0.6497 用作全系统参照，冻结 C1 权重只适合检查功率输入的兼容性。配对结果出现稳定收益后再讨论完整训练。

## 早期审查与评测口径

1. 完整验证的每视图保留上限是 300，单样本入口原来是 1,000。完整验证复核显示两值结果一致，`3172edd` 已将单样本默认值对齐到 300。比较新方案时沿用产生 0.6427 的验证口径。 [验证入口](../../scripts/validate_run.py) · [单样本入口](../../src/signals/infer.py)
2. 分类加权微调将同一项权重乘了两次。项目包装了 BCE，而 Ultralytics 8.4.155 也读取 `model.class_weights`，所以该分支的实际权重是平方。首场 baseline 的加权参数为零。若重新研究加权，先验证只乘一次，再从相同权重出发做单变量对照。 [项目实现](../../src/signals/train.py) · [上游损失实现](https://github.com/ultralytics/ultralytics/blob/v8.4.155/ultralytics/utils/loss.py#L395-L400)

## 视图归因的原始执行口径

OpenCode 在完整 1,543 个验证源上复核了每视图上限 300 与 1,000，两次报告的 mAP50、预测数量及边界扣留数量一致。入口参数可随本轮顺手对齐，验证参照采用 300。分类权重平方偏差也已核实，保留该次微调记录供解释，单次加权的效果仍待对照。 [复核结果](opencode-review.md)

1. 维持同一权重和完整验证集，跑一次所有视图，记录来源。在全局合并前分出粗图、细片、联合三组，再各自执行相同的全局 NMS 与每样本 100 框上限。联合组先复现 baseline mAP50 0.642701，并核对预测总数 65,025。
2. 按 `0/1/2`、`3/4/5` 和 `10/11` 汇报类别 AP、忽略类别的召回、TP/FP/FN，配少量代表性错例。将错类、重复和背景误检分开，记录边界扣留和近重复真值的影响。重叠框先按原有一对一规则匹配，保留真实近同框实例。
3. 按结果给出一个首选改动。正确框常被打错类，先试候选框分类复核。高分错误主要由某个视图引入，先试按来源重评分或合并。若有更直接的解释，在结果里写明依据。交付三组指标、关键错例和下一项建议，结果写回本共享目录。实验使用现有权重与验证集。

## 视图归因后的历史计划

每张细片覆盖约 2.93 MHz，单片预测与完整 20 MHz 或 40 MHz 真值框的 IoU 达不到 0.5。粗图保留宽带框的完整轮廓，细片保留窄带信号的频率细节。类别 `9/12/13` 的 AP@0.5 在细片为 0.7821、在粗图为 0.4838。宽带 `0–5` 的高分错类主要来自粗图，部分错类框的 IoU 超过 0.99。 [逐类分数和错例](../../reports/view_source_attribution.md)

1. **先做一次合并对照。**在全局合并前，仅去掉细片预测为 `0–5` 的候选框，保留所有粗图预测及其余细片预测。用 `3172edd` 归因的权重、验证集和合并参数，对照完整联合组与过滤组。报告总 mAP@0.5、各组 AP、忽略类别召回及误检数量。约 0.7 个百分点来自已有分组 AP 的粗算，以对照实测为准。
2. **优先验证粗图候选框的分类复核。**冻结检测器，第一轮优先看 `0/1/2`、`3/4/5`。在 fit 上用粗图预测框和匹配标签训练小分类器，纳入相似的错类与背景候选。固定 val 上使用检测器实际输出的候选框，比较原粗图裁块与同框回映射到原生 STFT 的裁块，记录输入大小和额外推理成本。检查高分错类、分组 AP 和合并后的总 mAP，依据对照结果决定是否纳入 `10/11` 或调整重评分。

## 协作方式

- GitHub `docs/collaboration/` 是共同交接入口。开工前拉取最新提交，先读本页的当前路线，再读该项实验的说明与已发布结果。长报告、配置和代码引用留在既有位置，通过链接查阅。
- 每次交接带上项目负责人的原始研究动机、推导思路和已权衡的代价，写清当前选择的理由、仍开放的决策、什么结果会改变选择。转发消息概括共同要回答的问题并链接仓库，技术说明保留方案分歧、已有证据和验证范围。
- 已确认的规格和待验证的设计选择写清楚。OpenCode 结合实际数据和服务器情况独立审查，可以提出替代方案。若判断不同，说明证据、适用条件和能区分它们的小实验，再决定下一步。
- 每个阶段完成后把实测结果、依据的提交或运行、偏离原方案的原因和建议写回相关记录并推送。给项目负责人先说进展、判断和下一步，附上能直接打开的 GitHub 文件链接。
