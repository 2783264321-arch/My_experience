# OpenCode 结果：fine-0-5 合并对照 + 粗图分类复核提案

依据 `docs/collaboration/README.md` 提交 `67a453a` 执行。固定
`best_corrected.pt`、完整 val（1543 源 / 24,975 views），一次 all-view 推理；
全局合并前把预测分成：

- **both**：全部 coarse + 全部 fine；
- **filtered**：全部 coarse + fine 中预测类别为 `6–13` 的框（去掉 fine 预测
  为 `0–5` 的框）。

两组使用相同 class-wise NMS（IoU 0.5）和每样本 100 框上限。
详细报告：[reports/fine_0_5_filter_comparison.md](../../reports/fine_0_5_filter_comparison.md)。

## 判断

1. **建议直接把 fine-0-5 过滤作为确定性后处理。** 免费 +0.70 pp，
   0/1/2 +1.92 pp、3/4/5 +1.35 pp，10/11 和窄带不受影响。
2. **它是精度清理，不是分类修复。** 高分错类和错类 GT 没变：
   0/1/2 530/997 错类、464 个 FP@0.5 错类；3/4/5 203/442、183；
   10/11 240/716、273。oracle-class AP 0.83–0.87 vs 实际 0.42–0.46，
   分类复核仍是主杠杆。
3. **10/11 不能一刀切过滤。** fine 仍贡献窄 10/11 实例的 TP；后续按带宽/
   来源门控。

## 粗图候选框分类复核提案

**优先级：0/1/2 → 3/4/5 → 10/11；6/7/8/9/12/13 不做分类，12/13 是小框
定位问题。**

第一轮（0–5）：

- 冻结检测器；使用 **coarse 视图 proposals**（不要用 fine 0–5）。
- 在 fit 上跑检测器，取 coarse proposals；IoU≥0.5 匹配 GT 作标签；加入
  高分未匹配框和跨类重叠框作 hard negatives；平衡 {0,1,2}、{3,4,5}。
- 固定 val 上使用检测器实际输出 proposals；训练小 CNN（ResNet18/4-block，
  128×256 或 256×256），6 类+背景头或两个 3 类头；类别平衡 + focal/CE。
- 评估 proposal 分类混淆，以及替换/固定融合检测器分数后的分组 AP、总
  mAP、高分错类和误检数；保持同一套 NMS/100 框。

**粗图裁块 vs 原生 STFT 裁块（同一预测框）：值得做，但作为第二层输入
ablation，不是第一轮。**

- 第一轮先用粗图裁块：匹配检测器输入，便宜；若 0–5 混淆基本解决，就不必
  做原生裁块。
- 若粗图裁块仍混淆，再用**同一 proposal 框、同一物理 context** 回映射到
  原生 STFT 功率裁块，重复同一分类器/划分/融合规则；这能判断 coarse 频率
  聚合是否是信息瓶颈。
- 实测（B=80/T=150，10% context）：20 MHz 的 coarse 裁块 616×286，
  原生 16,800×286；40 MHz 的 coarse 1,230×170，原生 33,601×170。
  裁块+resize 约 0.15–0.27 ms；ResNet18 前向约 0.07–0.15 ms/proposal；
  65k proposals 额外约 15–25 s，远小于整次推理。
- **注意**：原生裁块比 coarse 高 7–27 倍；直接 resize 到 128/256 会压缩
  100–260 倍，可能把要比较的细节抹掉。公平比较应使用更大输入
  （256×256/512×512）、1D 频率 profile 或 coarse+profile 双分支，并记录
  输入尺寸与成本。
- 同框、同物理 context、同结构/同 fit-val 划分/同融合规则；否则比较被
  输入尺寸/上下文污染。

若粗图分类器有效，再扩展到 10/11（10 MHz 用 coarse，窄实例用 fine）；否则
再考虑原生裁块、更大模型或成对混淆损失。test 继续封存。
